# پرامپت‌نویسی برای کد

کد تولیدشده را تا پیش از بازبینی و آزمون، غیرقابل‌اعتماد بدانید. پرامپت‌نویسی می‌تواند کار مهندسی را سریع‌تر کند، اما جای قراردادهای مخزن، بازبینی امنیتی یا کنترل‌های عملیاتی را نمی‌گیرد.

## تولید کد

پیش از تولید، زبان، runtime، framework و نسخهٔ وابستگی‌ها، رویه‌های مخزن، رفتار عمومی، ورودی‌ها، خروجی‌ها، خطاها، محدودیت‌های امنیتی و آزمون‌های لازم را مشخص کنید. رفتار وابستگی‌ها و نسخه‌ها را با manifest، lockfile و مستندات معتبر و فعلی پروژه اعتبارسنجی کنید.

## توضیح کد

توضیح را بر مبنای کد منبع و پیکربندی ارائه‌شده بنویسید. رفتار ناشناختهٔ runtime را ناشناخته اعلام کنید؛ وضعیت مخزن، تنظیمات استقرار یا وابستگیِ ارائه‌نشده را حدس نزنید.

## ترجمه یا مهاجرت کد

حفظ معنای مشاهده‌پذیر رفتار را الزام کنید. پیش از جایگزینی پیاده‌سازی، تفاوت‌های احتمالی در سیستم فایل، هم‌زمانی، خطا، runtime و سکو را مشخص کنید و سپس آزمون‌های رگرسیون را در برابر رفتار پیشین اجرا کنید.

## دیباگ یا بازبینی کد

شواهد قابل تکرار بخواهید و واقعیت‌های تأییدشده را از فرضیه‌ها جدا کنید. به‌جای وصلهٔ نشانه‌ها، رفع علت ریشه‌ای را ترجیح دهید، تغییر را حداقلی و قابل نگه‌داری نگه دارید و اثر آن بر امنیت و عملیات را بسنجید. برای قراردادهای کامل‌تر به الگوهای موجود دیباگ و تحویل کار مهندسی مراجعه کنید.

## اعتبارسنجی ایمن

برای «دیدن اینکه کار می‌کند»، کد تولیدشده یا کدی را که وضعیت را تغییر می‌دهد مستقیماً در محیط عملیاتی اجرا نکنید. برای سامانهٔ زنده با عیب‌یابی‌های فقط‌خواندنی آغاز کنید. هر لایهٔ معنادار و قابل‌اعمال—unit، integration و E2E—را پوشش دهید و اگر لایه‌ای واقعاً کاربرد ندارد، دلیل آن را مستند کنید. برای رفتاری که علت تغییر است، پوشش رگرسیون اضافه کنید.
